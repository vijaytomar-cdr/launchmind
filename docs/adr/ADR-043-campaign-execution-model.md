# ADR-043: Campaign Execution Model

**Status:** Accepted  
**Date:** 2026-07-08  
**Milestone:** 09 — Campaigns, Experiments & Execution

---

## Context

The existing `campaigns` table covers single-channel, single-status campaigns generated by the weekly brief pipeline. M09 requires campaigns to represent multi-channel growth initiatives with planning, scheduling, experiment linkage, approval audit trail, and failure recovery — without replacing or duplicating the existing model.

---

## Decision

### Extend, Not Replace

The existing `campaigns` table is extended additive-only with migration 051:
- `type TEXT` — 12 campaign type values
- `mission_id UUID` — link to mission that triggered this campaign
- `growth_brain_version INTEGER` — ICP version at campaign creation
- `scheduled_at TIMESTAMPTZ` — when to launch (null = manual)
- `cancelled_at TIMESTAMPTZ`
- `archived_at TIMESTAMPTZ`
- `failed_at TIMESTAMPTZ`
- `failure_reason TEXT`
- Status CHECK extended: adds 'scheduled', 'publishing', 'failed', 'cancelled', 'archived'
- Channel CHECK extended: adds 'app_store', 'play_store', 'push', 'twitter', 'tiktok', 'blog', 'product_hunt'

### Campaign Status State Machine

```
draft → pending_approval → approved → scheduled → publishing → launched
  ↓           ↓                ↓           ↓           ↓          ↓
archived   archived         archived    cancelled  failed     paused/completed/archived
```

### Campaign Types (12)

Stored in `campaigns.type`, validated by CHECK constraint:
`app_install` · `aso_improvement` · `review_generation` · `email` · `push_notification` · `social` · `paid_ad` · `product_hunt` · `india_launch` · `holiday` · `retention` · `win_back`

### Campaign Plan Generation

`POST /campaigns/:id/plan` calls the Context Engine + Sonnet to generate:
- Recommended channels
- Suggested assets
- Audience config
- Budget estimate
- Schedule

Result stored in `campaigns.audience_config` (JSONB) under a `plan` key.

### Approval Audit Trail

Separate `campaign_approvals` table (migration 053) tracks detailed approval history alongside the existing `campaigns.approved_at` column. Both must be consistent.

---

## Consequences

- All existing campaign routes remain backward compatible
- `approved_at` check in channels.route.ts is unchanged (§1.5 still enforced)
- Status machine enforced server-side; frontend cannot skip states
- Campaign types enable attribution reporting by initiative type
